# 무주택자 맞춤 임대주택·실거래 통합 플랫폼 설계

> 상태: 사용자 승인 완료
>
> 기준일: 2026-08-08
> 대상 저장소: `real-estate-sv`

## 1. 목적

기존 실거래 분석 서비스를 유지하면서, 청년을 포함한 모든 무주택자가 자기 조건에 맞는 임대주택과 주거비 지원을 찾을 수 있는 전국 단위 주거 의사결정 플랫폼으로 확장한다.

서비스는 두 질문에 답해야 한다.

1. 내 조건에서 신청할 수 있는 임대주택·지원제도는 무엇인가?
2. 원하는 지역의 실제 매매·전월세 가격은 얼마인가?

임대주택 경로는 신청 가능성과 예상 월 부담을 함께 비교하고, 실거래 경로는 지도에서 지역부터 단지·건물까지 바로 탐색한다. 두 경로는 첫 화면에서 동등하게 시작하되 결과 화면에서 서로 연결한다.

## 2. 범위

### 포함

- 전국 임대주택 모집공고
- 전국 청년·무주택자 대상 월세·보증금·이자 등 주거비 지원공고
- 로그인 없는 기본 질문 6~8개와 선택형 상세 질문
- 신청 가능성, 예상 월 부담, 초기자금, 마감일을 반영한 추천
- 진행 중 공고, 공식 원문, 준비서류, 확인할 조건 표시
- 지도 기반 지역 시세와 단지·건물 실거래 탐색
- 임대 결과에서 지역 실거래로, 실거래 상세에서 맞춤 주거비 계산으로 이동
- 개인 조건의 브라우저 로컬 저장
- 공고 출처, 기준일, 마지막 확인 시각, 데이터 상태 표시

### 첫 출시에서 제외

- 회원가입과 계정 간 조건 동기화
- 카카오톡·이메일·브라우저 푸시 알림
- 실제 청약 접수 대행
- 법적 효력이 있는 자격 판정
- 주민번호, 증빙서류, 금융계좌 등 민감정보 저장
- 모든 기관 공고의 첫 출시 동시 지원

공고 제공 범위는 전국이지만 기관 연결은 공식 데이터의 안정성과 중요도를 기준으로 순차 확대한다.

## 3. 승인된 제품 원칙

1. 첫 화면에는 `임대주택 맞춤 찾기`와 `지도에서 실거래 찾기`를 동등한 입구로 제공한다.
2. 임대주택 경로는 지도를 배경으로 유지하고 작은 팝업에서 질문을 진행한다.
3. 데스크톱 질문은 중앙 또는 우측 팝업, 모바일 질문은 하단 시트로 표시한다.
4. 실거래 경로는 질문 없이 지도에 즉시 진입한다.
5. 지도는 축소 상태에서 지역 시세·거래량을, 확대 상태에서 단지·건물 가격 핀을 표시한다.
6. 청년과 비청년 무주택자에게 동일한 기능을 제공하고 입력 조건에 따라 결과만 달리한다.
7. 추천 기본 정렬은 `신청 가능성 → 예상 월 부담 → 마감일`이다.
8. 개인 조건은 서버로 전송하거나 저장하지 않고 브라우저에만 저장한다.
9. 공고는 공식 데이터 우선 방식으로 수집하고 출처가 불명확한 값은 만들지 않는다.
10. 외부 알림은 맞춤 공고 화면과 마감 표시가 안정된 후 별도 단계로 구현한다.

## 4. 사용자 흐름

### 4.1 첫 화면

첫 접속 시 추가 질문이나 자동 분석을 실행하지 않는다. 다음 두 선택지를 보여준다.

- `내게 맞는 주거 찾기`: 임대주택, 지원제도, 예상 월 부담, 진행 공고
- `지도에서 실거래 찾기`: 지역 시세, 단지 가격, 매매·전월세 비교

두 카드의 시각적 비중은 같아야 한다. 임대주택은 특정 연령층만을 위한 기능처럼 표현하지 않는다.

### 4.2 임대주택 맞춤 찾기

임대주택 카드를 누르면 전국 지도를 유지한 상태로 질문 팝업을 연다.

기본 질문은 다음 범위에서 6~8개로 구성한다.

- 가구 유형
- 무주택 여부
- 정책상 나이 구간
- 소득 구간
- 자산 구간
- 희망 지역
- 현재 보증금·월세 또는 주거비
- 필요한 경우 학생·취업·신혼·고령자 등 특별 조건

한 화면에 모든 질문을 노출하지 않고 한 단계씩 진행한다. 희망 지역은 지도 선택과 검색 입력을 모두 지원하고 두 입력은 같은 상태를 사용한다.

질문 팝업을 닫아도 현재 입력은 브라우저에 임시 저장한다. 사용자는 언제든 `내 조건 수정`과 `내 조건 초기화`를 사용할 수 있다.

### 4.3 임대주택 결과

결과 첫 화면에는 정책 목록보다 사용자가 체감하는 결과를 먼저 표시한다.

- 현재 주거비 대비 예상 절감액
- 추천 선택지 3개
- 신청 가능성 상태
- 예상 월 부담
- 필요한 초기자금
- 신청 마감일
- 추가 확인 조건

각 추천 항목은 진행 중 공고, 공식 원문, 준비서류, 근거 규칙, 기준일과 연결한다. 결과에서 `이 지역 실거래 보기`를 누르면 희망 지역이 적용된 실거래 지도로 이동한다.

### 4.4 실거래 지도

실거래 카드를 누르면 지도에 즉시 진입한다.

- 축소: 시도·시군구·읍면동 단위 거래량과 대표 시세
- 확대: 현재 화면 안의 단지·건물 가격 핀
- 검색: 지역명, 단지명, 주소
- 필터: 매매·전세·월세, 주택 유형, 기준 기간
- 선택: 최근 거래, 전월세, 추세, 비교 분석

지도 확대 수준이 기준을 넘으면 지역 집계를 단지·건물 핀으로 전환한다. 핀은 현재 지도 영역에 필요한 데이터만 요청한다.

단지·건물 상세의 `내 조건으로 주거비 계산`은 선택한 지역과 확인 가능한 가격을 임대주택 질문 팝업에 미리 채운다.

## 5. 화면 구성요소

### 공통

- 서비스 헤더와 두 경로 이동
- 데이터 출처·상태·마지막 확인 시각
- 지역·단지·주소 통합 검색
- 데스크톱·모바일 반응형 지도

### 임대주택

- `HousingQuestionPopup`: 기본·상세 질문과 진행 상태
- `LocalProfileStore`: 브라우저 조건 저장·수정·초기화
- `HousingMatchSummary`: 예상 절감액과 추천 선택지 3개
- `HousingNoticeCard`: 신청 가능성, 비용, 마감, 출처
- `EligibilityEvidence`: 충족·미확인·불일치 조건과 근거
- `ApplicationChecklist`: 준비서류와 공식 신청 링크

### 실거래

- `MapSearch`: 지역·단지·주소 검색
- `RegionAggregateLayer`: 축소 상태 지역 거래량·대표 시세
- `PropertyMarkerLayer`: 확대 상태 단지·건물 가격 핀
- `PropertySummaryPanel`: 최근 거래와 전월세 요약
- 기존 실거래 목록·상세·기간 분석·3개 비교 기능

구현 시 현재 정적 프런트엔드 구조에 맞춰 각 책임을 별도 모듈로 나누고 `site/main.js`에 전체 로직을 추가하지 않는다.

## 6. 데이터 구조

### 6.1 공고

공고는 최소한 다음 값을 가진다.

- 내부 식별자
- 제공기관과 외부 공고 식별자
- 공식 원문 주소
- 공고 유형과 주택·지원 유형
- 제목과 요약
- 지역 코드와 지역명
- 모집·신청 시작일과 종료일
- 진행 상태
- 대상 조건과 확인 가능한 비용 조건
- 게시일, 원문 수정일, 마지막 수집 시각
- 정규화 상태와 품질 문제
- 원문 변경 감지용 해시

기관과 외부 식별자가 없으면 공식 원문 주소를 중복 판정에 사용한다. 같은 공고의 정정본은 별도 공고로 늘리지 않고 변경 이력으로 보존한다.

### 6.2 정책 규칙

자격 규칙에는 조건뿐 아니라 근거를 함께 저장한다.

- 적용 프로그램 또는 공고
- 조건 종류
- 비교 연산과 기준값
- 적용 시작일과 종료일
- 공식 출처와 조항 또는 안내문 위치
- 마지막 검증일
- 확정 조건인지 추가 확인 조건인지 구분

규칙이 없거나 해석이 모호하면 임의 판정하지 않는다.

### 6.3 사용자 조건

사용자 조건은 브라우저 저장소에만 보관한다.

- 가구·무주택·나이 구간
- 소득·자산 구간
- 특별 조건
- 희망 지역
- 현재 주거비와 초기자금 범위
- 마지막 수정 시각과 질문 버전

이름, 주민번호, 상세 증빙, 계좌정보는 입력받지 않는다.

## 7. 데이터 수집과 갱신

### 7.1 공식 데이터 우선

1. 공식 API·공개 피드가 있으면 이를 우선 사용한다.
2. 공식 데이터로 제공되지 않는 공고만 이용 조건을 확인한 공식 공고 페이지에서 보완한다.
3. 민간 블로그·커뮤니티·검색 요약은 공고 원천으로 사용하지 않는다.
4. 모든 화면에서 공식 원문으로 이동할 수 있어야 한다.

### 7.2 갱신 주기

기본 갱신 주기는 6시간이다. 기존 Cloudflare Worker의 예약 실행과 D1을 사용하며 별도 VPS나 24시간 PC에 의존하지 않는다.

수집 순서는 다음과 같다.

1. 원천 조회
2. 기관별 응답 정규화
3. 필수 값과 날짜 검증
4. 중복·정정공고 판정
5. 새 스냅샷 완전성 확인
6. 정상 스냅샷만 공개 상태로 전환

수집에 실패하거나 새 데이터가 불완전하면 기존 정상 스냅샷을 유지한다. 실패가 사용자 조회를 막지 않는 현재 D1 fallback 원칙을 재사용한다.

## 8. 맞춤 판정과 비용 계산

### 8.1 판정 상태

숫자 확률은 제공하지 않는다. 결과는 세 상태로 제한한다.

- `신청 가능성 높음`: 확인 가능한 필수조건을 모두 충족
- `추가 확인 필요`: 필요한 입력이나 공식 조건이 불완전
- `조건 불일치`: 확인 가능한 필수조건 중 하나 이상 불충족

필수조건을 먼저 적용하고 통과한 항목만 비용과 마감일로 정렬한다. 기본 정렬은 신청 가능성, 낮은 월 부담, 가까운 마감일 순이다.

### 8.2 월 실부담

첫 출시의 월 실부담은 다음 항목만 사용한다.

`월 실부담 = 월세 + 대출 월이자 - 확인 가능한 월 지원금`

- 보증금과 본인 부담금은 초기자금으로 별도 표시한다.
- 관리비는 공식 공고에서 확인되는 경우만 별도 항목으로 표시한다.
- 보증금의 기회비용과 확인되지 않은 지원금은 계산하지 않는다.
- 사용한 금액과 제외한 금액을 결과 상세에서 공개한다.
- 공고가 범위 금액만 제공하면 최솟값·최댓값 범위로 표시한다.

## 9. API와 데이터 흐름

브라우저는 공개 공고·규칙·지도 데이터만 서버에서 받는다. 개인 조건을 포함한 맞춤 판정과 비용 계산은 브라우저에서 실행한다.

필요한 읽기 계약은 다음 책임으로 분리한다.

- 진행 공고 목록과 지역·유형 필터
- 공고 상세와 공식 근거
- 공개 정책 규칙 버전
- 지도 지역 집계
- 현재 지도 영역의 단지·건물 요약
- 기존 실거래·전월세·기간 분석 API

서버 응답에는 데이터 출처, 상태, 갱신 시각을 포함한다. 지도는 전체 전국 단지 데이터를 한 번에 내려받지 않는다.

## 10. 오류와 불확실성 처리

### 공고 수집 실패

- 기존 정상 데이터를 계속 제공한다.
- `갱신 지연`과 마지막 정상 확인 시각을 표시한다.
- 실패한 새 응답으로 기존 데이터를 덮어쓰지 않는다.

### 조건 부족

- 결과를 숨기지 않고 `추가 확인 필요`로 표시한다.
- 필요한 질문만 다시 요청한다.

### 규칙 해석 불가

- 추정값을 만들지 않는다.
- `공식기관 확인 필요`와 공식 원문을 표시한다.

### 지도 데이터 부족

- 단지 핀을 만들 수 없으면 지역 집계 상태를 유지한다.
- 주소나 단지명이 모호하면 후보를 분리하고 자동 병합하지 않는다.

### 결과 없음

- 빈 화면 대신 희망 지역 확대, 조건 수정, 마감 공고 포함 여부 확인을 제안한다.
- 조건을 자동 완화하거나 사용자가 입력하지 않은 값을 가정하지 않는다.

## 11. 보안과 개인정보

- 공식 API 키와 외부 인증값은 기존 방식대로 Cloudflare Secret에만 저장한다.
- 브라우저에는 공개 공고·공개 규칙만 제공한다.
- 개인 조건은 브라우저에서만 처리한다.
- 공고 검색·지도 API에 입력 검증과 기존 Rate Limit 원칙을 적용한다.
- 공식 원문 요약을 화면에 표시할 때 HTML을 신뢰하지 않고 텍스트로 정제한다.
- 관리자 수집 상태는 기존 보호된 관리자 API 범위에 추가한다.

## 12. 성능 기준

- 첫 지도는 지역 집계만 요청한다.
- 단지·건물 핀은 확대 수준과 현재 지도 영역을 기준으로 지연 조회한다.
- 동일 지도 영역과 필터 결과는 짧게 캐시한다.
- 질문 팝업은 지도 재로딩 없이 열고 닫는다.
- 공고 결과는 진행 중 공고를 우선하고 페이지 단위로 제공한다.
- 지도 이동 중 오래된 요청 결과가 최신 화면을 덮어쓰지 못하게 한다.

- 중복·정정·마감·지역 분류
- 새 수집 실패 시 기존 정상 스냅샷 보존
- 출처·원문·마지막 확인 시각 유지

### 맞춤 판정

- 필수조건 충족·누락·불일치 상태
- 추천 정렬 안정성
- 월 실부담과 초기자금 분리
- 범위 금액과 제외 항목 표시

### 지도와 화면

- 축소 지역 집계와 확대 단지 핀 전환
- 지도 영역 밖 데이터 미요청
- 검색과 지도 선택 상태 일치
- 데스크톱 팝업과 모바일 하단 시트
- 팝업을 닫고 다시 열었을 때 조건 복원
- 키보드 조작, 포커스 이동, 팝업 닫기 접근성

### 회귀

- 기존 매매·전월세 조회
- 기간 분석과 3개 비교
- 거래 상세와 PNU·공법 데이터
- 관리자 데이터 상태
- 타입 검사, 전체 테스트, 프런트 문법 검사, 배포용 빌드

## 14. 구현 경계

구현 계획은 다음 독립 단위로 나눈다.

1. 두 개의 입구와 지도 셸
2. 지도 위 질문 팝업과 브라우저 조건 저장
3. 공고 수집·정규화·D1 스냅샷
4. 공개 규칙과 브라우저 맞춤 판정
5. 월 실부담·추천 결과·공고 상세
6. 지역 집계 지도와 기존 분석 연결
7. 단지·건물 핀과 양방향 교차 이동
8. 관리자 상태·전체 QA·보안 검토

각 단위는 로컬 구현과 검증을 먼저 수행한다. 운영 D1 변경, 예약 수집 활성화, 배포, 푸시는 각각 별도 승인 대상으로 유지한다.

## 15. 완료 조건

- 사용자가 첫 화면에서 임대주택 또는 실거래 경로를 바로 선택할 수 있다.
- 임대주택 질문은 지도 전체를 가리지 않는다.
- 맞춤 결과가 신청 가능성, 월 실부담, 초기자금, 마감일과 공식 근거를 제공한다.
- 실거래 지도는 지역 집계에서 단지·건물 핀으로 전환된다.
- 두 경로가 선택 지역과 가격 조건을 유지한 채 서로 이동한다.
- 개인 조건이 서버로 전송되거나 저장되지 않는다.
- 공고 갱신 실패가 기존 정상 데이터를 손상하지 않는다.
- 기존 실거래 기능의 회귀가 없고 정의된 검증이 통과한다.
